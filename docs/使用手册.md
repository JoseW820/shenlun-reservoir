## 核心设计：抓取 / 存储 / 展示 三层解耦

这是这套工作流最重要的设计。它解决的是「**筛选会不会把好东西筛掉**」这个问题。

```
① 抓取层  fetch_daily.py（每天 19:30）
     抓所有源 → 过滤通稿 → 判重 → 写入索引
     └─ 每天抓，所以「快照型」源（feed 只含 1-2 天的）不会丢内容
            ↓
② 索引层  index.sqlite（SQLite，304 条…，永不删除）
     └─ ★「长期来看信息没有遗漏」由这一层保证
     └─ 没被清单挑中的仍在这里，可检索、可回看
            ↓
③ 展示层  weekly_digest.py（每周日 20:00）
     从索引取 status='new' 的候选 → 按源配额 + 类型上限排序 → 挑 15 条
     └─ ★「每周只看 15 条」由这一层保证
     └─ 挑中的标记为 shown，下期不再出现
```

**关键点：筛选不再等于丢失。** 展示层每期只挑 15 条，但没被挑中的（当前有 229 条）**仍在索引里**。所以：

- 以后想加筛选规则（关键词加权、标题过滤、长度门槛）都**不会有丢失风险**——最坏情况只是某条没浮上来
- 想看更多 = 对索引做一次查询，而不是调大配额
- 快照型源（人民日报电子版 feed 只有当天报纸）**不会再丢 6/7 的内容**，因为每天都抓

> **为什么必须每天抓**：实测发现源分两类——「归档型」（半月谈基层治理的 feed 含 137 天）和「快照型」（人民日报电子版的 feed 只有 1 天）。周跑的话，快照型源只会抓到运行当天那一份，周一至周六全部丢失，而且**你完全看不见这个丢失**。

## 一、手动运行

### 每天抓取（入库）

```powershell
python D:\公考工作流\fetch_daily.py
```

启动 RSSHub → 并行抓 11 个源 → 过滤通稿 → 判重 → 写入索引 → 关掉 RSSHub。约 20-90 秒（瓶颈是最慢的那个上游站，不再是总和）。

**它不生成清单**，只往索引里加东西。

### 每周出清单

```powershell
python D:\公考工作流\weekly_digest.py
```

从索引挑 15 条 → 生成清单。**不抓取，所以是秒级完成。**

### 看索引现状

```powershell
python D:\公考工作流\fetch_daily.py --stats
```

会显示：索引总数、各状态计数、时间跨度、待展示条目按来源的分布。

跑完清单在 `<你的桌面>\公考素材\` 里，文件名形如 `2026-W40_素材清单.md`。

每次生成三个文件：

| 文件 | 用途 |
|---|---|
| `2026-W40_素材清单.html` | **看这个。** 双击用浏览器打开，链接直接可点，点过的条目自动变淡 |
| `2026-W40_素材清单.md` | Markdown 版。想用 Obsidian / Typora 打开、或想加批注时用 |
| `2026-W40_素材清单.json` | 机器可读版，给以后做自动化用，不用管 |

### 关于"链接点不动"

这是常见困惑，原因是不同软件对 Markdown 的支持不一样：

| 软件 | 情况 |
|---|---|
| **记事本** | 纯文本编辑器，**不渲染 Markdown**，永远不会有可点的链接。换工具 |
| **VS Code（编辑视图）** | Markdown 链接默认不可点，但裸链接可以 **`Ctrl + 点击`** |
| **VS Code（预览）** | 按 **`Ctrl + Shift + V`**，链接就能直接点 |
| **Obsidian / Typora** | 打开即渲染，链接可点 |
| **浏览器（本工作流的 `.html`）** | **双击即用，无需任何设置** ← 推荐 |

**所以直接用 `.html` 就行。** Markdown 版也做了兼容——标题是链接（预览里可点），下面另起一行放了裸链接（编辑器里可 `Ctrl+点击`）。

**HTML 版的小功能**：点过的条目会变淡并显示"✓ 已点开"，顶部有"已点开 N 条"计数。这个记录存在浏览器本地，**换浏览器或清缓存会重置**。


**常用参数：**

`fetch_daily.py`（每日抓取）：

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只报告，不写索引 |
| `--stats` | 只看索引现状，不抓取 |
| `--check-routes` | 源健康体检：探测全部路由可用性（含停用源），改配置后跑一次 |
| `--only banyuetan-jicengzhili,people-paper` | 只跑指定源，调试单个源用 |
| `--keep-running` | 跑完不关 RSSHub |

`weekly_digest.py`（每周出清单）：

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只报告，不写文件、不改索引 |
| `--date 2026-10-11` | 指定清单日期，影响文件名里的周次 |
| `--config 别的配置.json` | 用别的配置文件 |

**耗时**：每日抓取约 20 秒（RSSHub 生产模式启动约 2 秒 + 11 个源并行抓取十几秒）；每周出清单**秒级完成**（只读索引，不抓取）。

## 二、自动运行（两个任务）

需要**两个**任务计划：一个每天抓取入库，一个每周出清单。

| 任务名 | 频率 | 脚本 | 作用 |
|---|---|---|---|
| `公考素材每日抓取` | **每天 19:30** | `fetch_daily.py` | 抓取入库，不生成清单 |
| `公考素材周清单` | **每周日 20:00** | `weekly_digest.py` | 从索引挑 15 条出清单 |

**为什么每日在前、每周在后**：周日 19:30 先抓一遍，20:00 再出清单，这样当天的内容也包含在内。

在 PowerShell 里执行下面整段（**需要管理员权限**，因为要写系统任务）：

```powershell
$python = '<你的用户目录>\AppData\Local\Programs\Python\Python312\python.exe'
$dir    = 'D:\公考工作流'
$settings = New-ScheduledTaskSettingsSet -StartWhenAvailable -DontStopOnIdleEnd `
            -ExecutionTimeLimit (New-TimeSpan -Minutes 30)

# ① 每日抓取入库
Register-ScheduledTask -TaskName '公考素材每日抓取' -Force `
  -Action  (New-ScheduledTaskAction -Execute $python -Argument "`"$dir\fetch_daily.py`"" -WorkingDirectory $dir) `
  -Trigger (New-ScheduledTaskTrigger -Daily -At 7:30PM) `
  -Settings $settings -Description '每天抓取素材写入索引（不生成清单）'

# ② 每周出清单
Register-ScheduledTask -TaskName '公考素材周清单' -Force `
  -Action  (New-ScheduledTaskAction -Execute $python -Argument "`"$dir\weekly_digest.py`"" -WorkingDirectory $dir) `
  -Trigger (New-ScheduledTaskTrigger -Weekly -DaysOfWeek Sunday -At 8:00PM) `
  -Settings $settings -Description '每周从索引生成公考素材候选清单'
```

改时间就重新执行对应那段，把 `-At 7:30PM` / `-At 8:00PM` 换掉。

**常用操作：**

```powershell
# 立刻试跑
Start-ScheduledTask -TaskName '公考素材每日抓取'
Start-ScheduledTask -TaskName '公考素材周清单'

# 看运行结果（LastTaskResult 为 0 表示成功）
Get-ScheduledTaskInfo -TaskName '公考素材每日抓取' | Select-Object LastRunTime,LastTaskResult,NextRunTime
Get-ScheduledTaskInfo -TaskName '公考素材周清单'   | Select-Object LastRunTime,LastTaskResult,NextRunTime

# 两个任务一起看
Get-ScheduledTask -TaskName '公考素材*' | ForEach-Object {
    $i = Get-ScheduledTaskInfo -TaskName $_.TaskName
    '{0,-16} {1,-8} 下次 {2}' -f $_.TaskName, $_.State, $i.NextRunTime
}

# 删除
Unregister-ScheduledTask -TaskName '公考素材每日抓取' -Confirm:$false
Unregister-ScheduledTask -TaskName '公考素材周清单'   -Confirm:$false
```

> 任务运行时**不会弹窗**（隐藏运行）。如果你想看着它跑，就用手动方式（第一节）。

## 三、调整工作流

所有调整都在 `sources.json` 里，**改完不用动代码**。

### 3.1 加一个源

在 `sources` 数组里加一项，然后跑一遍源健康体检确认可用：

```powershell
python D:\公考工作流\fetch_daily.py --check-routes
```

字段说明：

| 字段 | 说明 |
|---|---|
| `id` | 唯一标识，用于 `--only` |
| `name` | 清单里显示的名字 |
| `type` | `案例型` / `论述型`，决定它在清单里的分组。**类型清单不是写死的**，由 `typeCaps` 的键顺序决定 |
| `path` | RSSHub 路由，如 `/banyuetan/jicengzhili` |
| `quota` | 每周最多取几条 |
| `enabled` | `false` 可临时停用而不删配置 |
| `suggestCollection` | 默认建议归入的 Zotero 集合（会被下面的关键词规则覆盖） |

**找可用路由**：跑 `python D:\公考工作流\tools\inventory_routes.py`，它会列出 RSSHub 里有哪些源。RSSHub 有 2014 个 namespace，你的来源基本都有。

**注意**：新源一定要先用 `--check-routes` 验一遍。已实测**约 1/3 的路由会因为官网改版而失效**（表现为 HTTP 503，因为 RSSHub 在解析到 0 条内容时返回 503）。

### 3.2 调通稿黑名单

`titleFilter` 是两级设计，这是过滤质量的关键：

- **`hardBlock`**：命中即剔除，无豁免。放的是仪式性/程序性内容（升国旗、招待会、任免、体育赛事、天气预警、招标公告…）
- **`softBlock`**：命中后，**若标题还含 `policySignals` 任一词就保留**。放的是可能有两种性质的内容（座谈会、表彰、事故通报…）

**几个刻意的设计，改之前请先理解：**

- **`会议` 不在黑名单里** —— "国务院常务会议部署…"是核心素材，杀了就亏大了
- **`体育` 不杀，只杀赛事动词** —— "发展体育赛事激发消费活力的意见"是好素材；"中国男排完胜泰国队"才该杀。所以用的是"完胜/夺冠/晋级"这类词
- **`事故/伤亡` 放二级** —— 事故通报无价值，但"提升灾害治理能力""安全生产机制"有价值

误杀了就往 `hardBlock` 里删词、或往 `policySignals` 里加词。

### 3.3 调数量与配比

| 配置项 | 说明 |
|---|---|
| `listTarget` | 清单总条数上限（当前 **15**） |
| `weeklyReadLimit` | 你每周的阅读上限，只影响清单头部的提示文字（当前 **15**） |
| `typeCaps` | 各类型条数上限，**保证每类都出现** |
| 各源的 `quota` | 单源上限 |
| `backlog.staleAfterDays` | 超过 N 天仍未展示的条目标 `stale`，不再参与挑选（默认 28；不删数据，把 `status` 改回 `new` 即可恢复；设 0 关闭） |

当前配比：**案例型 10 · 论述型 5**。

**为什么是 10:5**：11 份申论真题实测下来，材料型题目（归纳概括 + 词句理解 + 提出对策）合计 **440 分**，论述型（公文写作 + 大作文）合计 **245 分**，约 **64:36** → 对应 15 条里的 10:5。

**配额与上限的关系**：各源 `quota` 之和是「可用量」，`typeCaps` 是每类的硬上限，`listTarget` 是总量上限。

> **当前三者是精确对齐的**：案例型 quota 之和 = 10 = `typeCaps.案例型`；论述型 quota 之和 = 5 = `typeCaps.论述型`；总量 = 15 = `listTarget`。
> 所以**类型上限和总量上限这两步目前不裁剪任何东西**（运行日志里显示「被类型上限/总量裁掉 0 条」）。
> 真正决定选哪 15 条的，只有「**每个源取最新 N 条**」这一条规则。`typeCaps` / `listTarget` 是安全网 —— 当你想让某些源多产、靠上限来兜配比时才会生效。

**配额裁不完会自动回填**：各源先独立取 `quota` 条；若合计不足 `listTarget`（比如某源本周没新内容），会从各源配额之外的剩余候选里按「类型优先 + 时间倒序」**补满**，只受 `typeCaps` 约束。所以清单不会因个别源断更而变短。

**积压有治理，不会只涨不消**：超过 `backlog.staleAfterDays` 天仍未展示的条目标 `stale`（挑选按日期倒序，老条目数学上永远浮不上来，不如明确标出）；停用源的存量标 `archived`。两者都只改状态、不删数据，想恢复改回 `new` 即可。

**清单里的类型顺序由 `typeCaps` 的键顺序决定**，代码里没有写死。以后想恢复数据型，只要在 `typeCaps` 里加回 `"数据型": N`，并把对应源的 `enabled` 改回 `true` 即可。

### 3.4 调输出格式

`outputFormats`（当前 `["html", "md", "json"]`）控制每次生成哪些文件。

- 只想留 HTML：改成 `["html"]`
- 想要 HTML + Markdown：改成 `["html", "md"]`

**建议保留 `html`** ——那是你实际用来点链接、标记已读的界面。

### 3.5 调摘要长度

`summary.chars`（当前 110 字）控制每条摘要的长度。`summary.maxSourceChars`（当前 20000）是防爆保护——国家统计局的正文有 17 万字，不截断会撑爆清单。

> **用记事本编辑 `sources.json` 是安全的**：Windows 记事本保存时会写入 BOM，脚本已做兼容（用 `utf-8-sig` 读取）。但**改完请确保 JSON 格式正确**（引号、逗号），改坏了脚本会报 `JSONDecodeError` 并指出出错行号。

## 四、去重机制（重要，值得看懂）

清单最怕的就是「重复」。这套去重是**两层判定 × 三个基准**，逻辑如下。

### 4.1 两层判定：URL 和标题

只按 URL 去重是不够的——**同一篇文章经常以不同链接出现在多个源**。比如一篇新华社稿，人民日报和求是网各自转载，URL 完全不同。所以再加一层标题判定。

| 判定层 | 指纹算法 | 能挡住什么 |
|---|---|---|
| **URL** | 统一 `http`/`https`、去掉 `www.`、去锚点、去 `utm_*` 等跟踪参数、去尾部斜杠 | 同一个页面的不同写法 |
| **标题** | 剥掉来源后缀（`_中国政府网`）、栏目后缀（`- 求是网`）、装饰括号（`（组图）`），再去掉所有标点和空白 | **同一篇文章的不同链接**（跨源转载） |

**标题指纹有个长度闸门**：少于 8 个字（如「宏观数据」「通知」）不参与标题判定，只走 URL 判定。因为太短的标题容易把**不同**文章错判成同一篇，那种误判会让你**漏掉真的素材**——比重复更糟。

### 4.2 三个基准

| 基准 | 来源 | 检查时机 | 作用 |
|---|---|---|---|
| **Zotero** | 你的 Zotero 库（URL + 标题） | 抓取时 + 展示前各查一次 | 你已经存过的，不再入库、不再给你 |
| **索引** | `index.sqlite` 里全部条目 | 抓取时 | 抓过的不再重复入库（幂等） |
| **已展示** | `index.sqlite` 里 `status='shown'` 的条目 | 展示层 | **上周及以前给过你的，不再出现** |
| **本次运行** | 内存中的本次已选集合 | 抓取时 | 同一篇被多个源同时收录时，只留一条 |

**跨周去重靠索引的 `status` 字段**：清单生成后，被挑中的 15 条标记为 `shown`，下期查询只取 `status='new'`。所以**第一周取过的，第二周不会再出现**（已实测：交集 0）。

展示前会**再查一次 Zotero**——因为抓取入库之后，你可能又存了一些。那些会被标记成 `in_zotero` 并排除。

### 4.3 Zotero 读取的三级降级

这一步曾经是个坑：**Zotero 运行时，直接读数据库会被锁死**（`database is locked`），去重静默失效。现在改成三级降级：

| 顺序 | 方式 | 适用场景 | 读得到最新吗 |
|---|---|---|---|
| 1 | Zotero 本地 HTTP API（端口 23119） | **Zotero 运行时**（最可靠） | ✅ 实时 |
| 2 | 数据库只读打开（`mode=ro`） | Zotero 已关闭 | ✅ 最新 |
| 3 | **连 WAL 一起复制后读** | Zotero 运行但 API 不可用 | ✅ 最新 |
| 4 | 数据库快照（`immutable`） | 前三种都不行时的保底 | ⚠️ **忽略 WAL，可能偏旧** |

三级都失败时，会在**清单顶部显示醒目警告**，而不是默默给你重复条目。

> **为什么第 3 步重要**：SQLite 的 `immutable=1` 会**忽略 WAL 日志**。
> 实测你的 Zotero 主库 5.5 MB、WAL 却有 **16.4 MB** —— 也就是说大量最近的改动还没写回主库。
> 早期这个工具直接用 `immutable=1`，结果**读到了过期的分类树**（你刚重排过层级，它却报「集合找不到」）。
> 所以现在改成把 `.sqlite` + `-wal` + `-shm` 一起复制到临时目录再读，读完即删。

> 前提：Zotero 里要勾选 **设置 → 高级 →「允许其他应用程序与此计算机上的 Zotero 通信」**（你的已经开了，实测 API 可用）。
> 若哪天关掉了，第 2/3 步仍能保证去重正确。

**顺带一提**：`tools\check_collection_names.py` 原来也是直接用 `immutable=1`，所以它会在你改完分类树后
**误报「集合找不到」**。已修成同样的「API 优先」顺序。

### 4.4 已知局限

- **标题被改写且 URL 也不同的转载**挡不住。例如某稿从「A 市经验」改题为「B 市做法」再发一次。
- **Zotero 里的短标题**（你用脚本设的那种，如「宏观经济与财政」）**无法参与标题判定**，只能靠 URL 命中。所以别指望标题层能覆盖 Zotero 里的老条目。
- 索引记的是「**已经展示给你**」，不是「你已经读过」。你跳过没看的条目不会再出现在清单里，**但它仍在索引中**，可以查询回看。

### 4.5 确定性剔除（形态噪音）

除了去重，还有一层**确定性剔除**：把形态上明确无价值的东西挑出来，标记为 `status='junk'`，不再展示。

**它只处理「形态」，不做主题或质量判断** —— 所以不存在误判好素材的风险。而且只是改状态、不删数据，随时可以改回来。

| 规则 | 例子 | 实测命中 |
|---|---|---|
| 报刊版面责任署名 | `一版责编：胡安琪 郭雪岩 赵 政…`、`本版责编：韩 鑫` | 4 条 |
| 无正文形态（整条标题就是） | `图片报道`、`组图`、`视频`、`海报` | 1 条 |
| 礼节性节日祝贺/问候 | `习近平向全国广大农民…致以节日祝贺和诚挚问候` | 2 条 |
| 纯活动预告 | `中国科协"开放合作月"系列活动将于10月启幕` | 1 条 |
| 版面目录 | `目录`、`本期目录` | 0 条（备用） |

**合并净剔除 8 / 315 条 = 2.5%。**

> **注意：「一图读懂《XX规划》」刻意不剔除。**
> 它不是垃圾，而是政策文件的可视化。真正的问题是：它和文字版《XX规划》解读会被判为重复，
> 如果图解版日期更新，**文字版反而会被判重删除，你就只拿到没正文的图解**。
> 所以对这类条目做的是**降序而非剔除** —— 排序时「有正文的版本」优先，
> 图解版排在同类之后。这样既不丢文件，又保证你拿到能读的版本。

规则写在 `weekly_digest.py` 的 `JUNK_PATTERNS` 与 `GRAPHIC_RE`。想调整直接改正则即可。

### 4.6 想重新开始

| 想做什么 | 怎么做 | 后果 |
|---|---|---|
| **让所有内容重新可展示** | 把索引里 `status` 从 `shown` 改回 `new` | 已给过的条目会再次出现 |
| **恢复被积压治理的条目** | 把 `status` 从 `stale` / `archived` 改回 `new` | 老条目重新参与挑选（但按日期倒序，太老的仍难浮上来） |
| **彻底从零开始** | 删除 `index.sqlite` | 索引里的一切都没了（**慎用**） |
| **只清空待展示池** | `DELETE FROM items WHERE status='new'` | 待展示的清掉，已展示的不动 |

改 `status` 用任意 SQLite 工具即可（例如 `python -c "import sqlite3; ..."`，注意别在 Zotero 运行时改 Zotero 的库）。

## 五、出问题怎么办

### 联网要求（两个脚本不一样）

| | 需要联网吗 | 说明 |
|---|---|---|
| **抓取 `fetch_daily.py`**（每天 19:30） | **必须联网** | RSSHub 虽然跑在本机，但它要去上游网站取内容。断网则所有源失败，索引不增长 |
| **出清单 `weekly_digest.py`**（每周日 20:00） | **不需要联网** | 只读本地 `index.sqlite` + 本地 Zotero。所以断网也能出清单，用的是本周已抓到的内容 |

> **这是三层解耦带来的好处**：抓取和展示互不依赖。所以偶尔断网/关机一两天，不会导致清单出不来——
> 只是这几天的内容没进索引而已。而且抓取任务设了 `StartWhenAvailable`，开机后会补跑一次。

**断网时抓取会怎样**：每个源单独失败、单独记录，脚本继续跑；如果**所有源都失败**，
脚本会打印诊断并以**退出码 2** 结束——这样计划任务的「上次运行结果」不是 0，你能看出问题。

手动查：
```powershell
# 看计划任务上次的退出码（0 = 正常，2 = 所有源都失败，通常是没联网）
Get-ScheduledTaskInfo -TaskName '公考素材每日抓取' | Select-Object LastRunTime, LastTaskResult
```

### 常见现象

| 现象 | 原因与处理 |
|---|---|
| 某源在清单底部显示 `HTTP 503` | 该路由失效（官网改版）。到 RSSHub 仓库提 issue，或先在 `sources.json` 里把该源 `enabled` 设为 `false` |
| 清单条目数突然很少 | 正常——`status='shown'` 的不会再出现。也可能某些源那几天没更新。跑 `fetch_daily.py --stats` 看索引里还有多少待展示 |
| 清单是空的 | 跑 `fetch_daily.py --stats`：若「待展示」为 0，说明索引都被挑过了，等下次抓取；若不为 0，检查各源 `quota` 与 `typeCaps` |
| `RSSHub 启动失败` | ① 确认 `D:\rsshub-engine` 存在；② 若刚移动过目录，在 `D:\rsshub-engine` 下执行 `$env:CI='true'; corepack pnpm install` 重装依赖；③ 确认路径是纯英文；④ 启动输出看 `logs\rsshub-boot.log`；⑤ 开发模式（tsx watch）启动慢且偶发假死，执行 `corepack pnpm build` 生成生产构建后会自动切到「启动约 2 秒」的生产模式 |
| **计划任务「上次运行结果」是 2** | **所有源都抓取失败**，通常是没联网，或 RSSHub 没起来。见上面的联网要求 |
| 想查某次计划任务为什么失败 | 看 `logs\fetch-YYYYMMDD.log` 或 `logs\weekly-YYYYMMDD.log`，有完整运行现场 |
| 清单顶部提示「索引最新抓取是 N 小时前」 | 每日抓取连续失败，清单用的是旧内容。手动跑一次 `fetch_daily.py`，并查 logs 找原因 |
| 想重来 | 见 4.5 节：改 `status` 可重新展示；删 `index.sqlite` 是彻底从零（会丢全部历史，慎用） |
| 摘要里出现奇怪的截断 | 源站版式变了，需要调 `weekly_digest.py` 里的 `NOISE_PATTERNS` / `SIGNATURE_LINE` |

### 电脑息屏 / 睡眠 / 合盖

**「息屏」和「睡眠」是两回事**，结果完全不同：

| 状态 | 任务能跑吗 |
|---|---|
| 只是显示器关闭（系统仍醒着） | ✅ 能跑 |
| 系统进入睡眠 | ❌ 不跑（但开机后补跑一次） |
| 合上笔记本盖子（默认触发睡眠） | ❌ 不跑（同样会补跑） |

两个任务都设了 `StartWhenAvailable`，**错过的会在电脑可用时补跑一次**，不会永久跳过。

想让息屏后照跑（**只改插电源时，不影响电池续航**）：

```powershell
powercfg /change standby-timeout-ac 0      # 插电源时永不睡眠
powercfg /change hibernate-timeout-ac 0    # 插电源时永不休眠
```

想连合盖也不睡（例如放包里插着电）：

```powershell
powercfg /setacvalueindex SCHEME_CURRENT SUB_BUTTONS LIDACTION 0
powercfg /setactive SCHEME_CURRENT
```

> 计划任务默认**「电池供电时不启动」**。这个工作流注册任务时已改为**允许电池供电**
> （每天只需几分钟网络，为可靠性值得）。想核对：
> `(Get-ScheduledTask -TaskName '公考素材每日抓取').Settings.DisallowStartIfOnBatteries` 应为 `False`。

## 六、这个工作流刻意不做的事

| 不做 | 原因 |
|---|---|
| **不做自动分类** | 找不到免费可用的中文政策分类器；且分类基本由来源决定，关键词规则已够 |

| **不做天津市政要闻** | RSSHub 的 `gov/tianjin` 只有"保税区公告""人才公告"两条，没有市政府要闻/政策路由 |

## 七、设计依据（为什么是这样）

清单的形态是从**历年申论真题**倒推出来的，不是拍脑袋定的。

### 7.1 真题实测（11 份申论卷：国考 2020–2026、天津 2022–2025）

**规模**：每卷给定资料约 **6,800 字**、**4-5 个材料**。

**题型与分值**（37 题 / 775 分）：

| 题型 | 题数 | 分值合计 | 平均 |
|---|---|---|---|
| 归纳概括 | 13 | 225 | 17 |
| **大作文** | 5 | **180** | **36** |
| 词句理解 | 7 | 160 | 23 |
| 公文写作 | 3 | 65 | 22 |
| 提出对策 | 3 | 55 | 18 |

→ **材料型（归纳概括 + 词句理解 + 对策）= 440 分**，**论述型（公文 + 大作文）= 245 分**，约 **64 : 36**。这就是 `typeCaps` 定 **10 : 5** 的依据。

**主题分布**（跨 11 卷累计词频）：

| 主题 | 频次 | | 主题 | 频次 |
|---|---|---|---|---|
| 科技创新/产业 | **420** | | 城市/区域发展 | 127 |
| 文化/文旅 | **302** | | 安全/应急 | 28 |
| 乡村振兴/农业 | **297** | | 党建/中央精神 | 24 |
| 民生/公共服务 | 228 | | **经济/财政金融** | **19** ← 最少 |
| 生态/能源 | 190 | | | |
| 基层治理/社区 | 187 | | | |
| 人才/干部 | 145 | | | |

→ 这是 P1 重排源与配额的依据。对照之下，改造前的配额**把最多的名额给了真题里排第 6 的「基层治理」**，而排第 2 的「文化/文旅」**完全没有源**。

**材料形态**（这条决定选材偏好）：

| 特征 | 出现次数 |
|---|---|
| 人物直接引语（"…"某某说） | **667** |
| 具体地名（某某县/镇/村/社区） | **352** |
| 做法动词（建立/推行/打造…） | 157 |
| 企业机构名 | 147 |
| 具体数字（带单位） | 127 |
| 问题类词（困难/不足/瓶颈） | 89 |
| **政策文件引用（《…》）** | **23** ← 极少 |

→ **给定资料几乎不引用政策文件原文**，而是"真实地名 + 人物原话 + 具体做法"。所以案例型素材是主体；但政策文件仍要保留，因为大作文需要它积累语言。

### 7.2 为什么没有加"打分/加权"筛选规则

曾经打算加「含具体地名 +1、含人物引语 +1」这类规则，**在真实候选数据上实测后被否掉了**：

| 信号 | 实测 | 结论 |
|---|---|---|
| **地名** | 严格匹配（只认真实行政区划后缀）只覆盖 **5.4%**（17/315）；在最需要的源上几乎为零——人民网·科技 **0/28**、旅游 1/28、求是网·理论文选 1/37 | **太稀疏，无法给 28 条候选排序** |
| **引语** | 标题含引号占 **29.2%**，但看实例是「跑出"加速度"」「巨型"充电宝"」这类**修辞引号**，不是人物引语 | 太普遍，区分度低 |
| **形态词** | 「一图读懂/组图/视频」只占 **3%**，且集中在已停用的源 | 降权无价值 |

还有一个反例说明问题：按地名排序时，求是网·原创的**义乌三条**被提到了最前——它们**确实是典型调研案例**，但被提上来的原因是「**县域**」里的「县」字命中了正则。**结果对，机制错。** 靠正则抓特征容易得到"看起来对但不可靠"的结果。

所以改为：
1. **只做确定性剔除**（形态层面的明确噪音，见 4.5）
2. **打分/排序规则暂不做**，改为积累真实反馈——对照索引里 `status='shown'` 的条目与你的 Zotero，算出各源的"命中率"，用实际行为而不是猜测来调配额。工具见 `tools\audit_hitrate.py`。

详见 `docs\方案-重整版.md`。
